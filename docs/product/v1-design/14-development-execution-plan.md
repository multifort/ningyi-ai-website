# 14 后续开发执行计划与进度

> 基线日期：2026-09-28。本文是后续研发任务、依赖、进度和退出条件的唯一执行主表；`08-implementation-roadmap.md` 保留长期阶段定义，`13-current-implementation-status.md` 保留当前代码事实。任务完成后必须同时更新本文状态和 `13-current-implementation-status.md` 的验证证据。

## 1. 目标与范围

后续研发以 `01-scope-traceability.md` 的成功定义为准：标准项目在没有人工处理用户项目的情况下，从多格式输入稳定形成七类一致、可追溯、可修改、可下载、可删除的成果，并通过独立自动质量门。

当前计划覆盖：

- 修复验收答案进入生成链路的问题，恢复基准项目作为独立质量证据的可信性。
- 建立仓库内可重复的浏览器、服务端、渲染和视觉回归。
- 补齐 BM-13—18、企业模板、旧 Office 和 AI Agent 项目覆盖。
- 完成 PostgreSQL、对象存储、生产安全、多 Worker 和容量验收。
- 完成 18 个基准项目、30 次连续无人值守活动和灰度开放门。

当前计划不覆盖：

- 支付、订单、套餐、发票、退款和计费中心。
- 多成员组织、审批流、完整在线 Office 编辑器和通用 Agent 编排平台。
- M9 的图像生成视觉方向与 HTML 到原生 PPTX 无损复原；仅完成 M3 所需的企业模板兼容和基础视觉质量门。
- Kubernetes、服务网格或微服务拆分。

## 3. 状态定义与执行规则

- `BLOCKED`：依赖尚未完成，不得并行推进会污染证据的后续任务。
- `READY`：依赖已满足，可以直接开始。
- `IN_PROGRESS`：正在实现或验证。
- `DONE`：代码、自动证据、文档和回退说明全部完成。
- `DEFERRED`：明确不进入当前灰度目标。

执行规则：

1. 先完成 G0，再继续创建 BM-13—18；避免继续扩大验收答案泄漏。
2. 每项任务必须引用 `REQ-`、`NFR-`、`SEC-` 或 `OPS-`，并附自动测试或基准证据。
3. `pnpm quality:check` 是本地统一质量门；仓库当前不使用 GitHub Actions。
4. 基准 manifest 摘要通过只证明包完整，不代表产品运行或内容质量通过。
5. 一个关卡退出前，更新本文状态、`13-current-implementation-status.md` 和受影响的规格/API/契约文档。

## 6. 进度维护模板

完成任务时在对应行更新状态，并在提交说明或进度记录中写明：

- 完成的任务 ID 和关联需求编号。
- 变更文件和迁移/回退边界。
- 实际执行的验证命令与结果。
- 新增或更新的基准运行报告位置。
- 尚未解决的风险及其依赖任务 ID。

禁止仅把状态改为 `DONE` 而没有自动证据；禁止用 manifest 完整性校验代替真实项目运行；禁止把一次性 `/tmp` 浏览器脚本作为仓库 E2E 完成证据。
