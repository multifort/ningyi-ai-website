# 03 七类成果详细规格

## 1. 共用规则

### 1.1 成果不是七次独立写作

七类成果从同一个正式项目模型读取事实、需求、功能、角色、工作量、计划、价格、术语和假设。模型负责理解与表达，程序负责编号、关系、公式、汇总、日期、版本、文件渲染和确定性检查。

### 1.2 共用字段

每个成果对象必须包含：

- `id`：稳定对象编号。
- `project_id`、`content_version_id`。
- `status`：草稿、候选、发布、受影响、失败或归档。
- `title`、`summary`、`sort_order`。
- `source_refs[]`：来源块和用户确认记录。
- `assumption_refs[]`：使用的假设。
- `dependency_refs[]`：上游项目对象。
- `visibility`：client、internal、both。
- `locked_fields[]`。
- `quality_results[]`。
- `created_by`：model、rule、user、migration。
- `created_at`、`updated_at`。

### 1.3 共用版本

- 内容版本 `V1、V2……`：语义和确定性数据发生变化。
- 渲染版本 `R1、R2……`：模板、Logo、颜色、版式或文件格式变化。
- 单个成果不得自行脱离项目内容版本发布。
- 渲染失败不创建新内容版本。

## 2. DEL-REQ 需求分析

### 2.1 目标

形成可追溯、可验收、可关联功能和范围变更的需求基线，不只生成需求说明文章。

### 2.2 核心对象

| 对象 | 必要字段 |
|---|---|
| Requirement | 编号、业务域、标题、描述、价值、优先级、状态、验收标准、来源、假设、相关角色/场景/功能 |
| BusinessDomain | 编号、名称、边界、目标、负责人角色 |
| Actor | 名称、类型、目标、权限范围 |
| Scenario | 触发、前置、主流程、异常、结果、参与角色 |
| Constraint | 类型、描述、强制程度、来源、受影响范围 |
| OpenIssue | 问题、影响、建议选项、状态 |

### 2.3 默认结构

1. 项目背景与目标。
2. 客户、用户与业务场景。
3. 范围、边界与不包含内容。
4. 需求总览与优先级。
5. 分业务域需求表。
6. 非功能需求。
7. 约束、依赖、假设与待确认项。
8. 需求—功能追踪矩阵。

### 2.4 展示与输出

- 在线：分组表格，可筛选优先级、状态、来源、无验收标准和冲突。
- XLSX：需求表、角色、场景、约束、追踪矩阵工作表。
- DOCX/PDF：需求分析报告和表格附录。

### 2.5 修改和影响

- 修改描述或优先级：影响相关功能、估算、计划、方案章节和 PPT 页面。
- 删除需求：默认标记取消，不直接物理删除；展示受影响对象后确认。
- 锁定需求：新材料只能形成冲突或建议，不能覆盖。

### 2.6 质量门

- 每条关键需求有来源或明确标记为用户确认/系统假设。
- 每条关键需求有可验证的验收标准。
- 编号唯一且稳定；删除或排序不复用编号。
- 重复需求、互斥需求和范围外需求已标记。
- 需求到功能的覆盖率达到验收门槛。

## 3. DEL-FUN 功能清单

### 3.1 目标

把需求转化为可估算、可规划和可验收的系统功能结构。

### 3.2 核心对象

| 对象 | 必要字段 |
|---|---|
| System | 名称、边界、终端、部署方式 |
| Module | 编号、名称、目标、所属系统、依赖 |
| Feature | 编号、名称、描述、规则、输入、输出、权限、数据、接口、异常、复杂度、相关需求 |
| Integration | 外部系统、方向、方式、数据、频率、认证、失败策略 |
| DataEntity | 名称、用途、关键字段、生命周期、敏感级别 |
| AgentCapability | 任务、知识、工具、权限、记忆、输入输出、评测、失败降级 |

### 3.3 默认结构

1. 产品/系统与终端总览。
2. 模块层级。
3. 功能清单。
4. 业务规则和权限。
5. 数据对象。
6. 外部接口。
7. AI Agent 能力（如适用）。
8. 需求—功能覆盖矩阵。

### 3.4 展示与输出

- 在线：系统—模块—功能树和可筛选表格。
- XLSX：系统、模块、功能、规则、接口、数据、Agent 和追踪矩阵工作表。
- DOCX/PDF：功能规格摘要及详细附录。

### 3.5 修改和影响

- 新增/删除功能影响估算、周期、报价、实施计划、方案架构和 PPT。
- 修改复杂度属于语义修改与重新计算组合：模型给出理由，规则引擎计算人天。
- 修改接口必须检查安全、部署、依赖和第三方成本。

### 3.6 质量门

- 功能有明确系统和模块归属。
- 关键功能有相关需求，不允许无来源“凭空扩展”。
- 需求覆盖缺口、孤立功能和重复功能为显式检查结果。
- Agent 能力必须定义权限、外部动作边界、评测和失败降级。

## 4. DEL-EST 工作量估算

### 4.1 目标

输出可解释、可调参、可重新计算的角色工作量，而不是让模型直接猜总人天。

### 4.2 核心对象

| 对象 | 必要字段 |
|---|---|
| EstimationItem | 相关功能/工作包、基准人天、复杂度、复用、接口、安全、不确定性系数、理由 |
| RoleEffort | 角色、阶段、人天、分配规则 |
| EstimationScenario | 低/基准/高、总人天、假设、风险储备 |
| RateCard | 角色、内部成本、客户日单价、有效期、可见范围 |

### 4.3 计算原则

```text
调整人天 = 基准人天
        × 复杂度系数
        × 复用系数
        × 接口系数
        × 安全系数
        × 不确定性系数
```

模型只判断分类和理由；系数、汇总、舍入和角色分配由规则引擎执行。所有参数保留版本与来源。

### 4.4 展示与输出

- 在线：功能/工作包明细、角色汇总、阶段汇总和三档场景。
- XLSX：参数、功能估算、角色汇总、阶段汇总、场景和假设工作表；公式可编辑。
- PDF：客户可见估算摘要。

### 4.5 修改和影响

- 日单价、税率不影响人天；复杂度和范围影响人天。
- 用户修改单项参数后程序重新计算所有下游汇总，不调用模型。
- 模型重判复杂度时只处理受影响功能。

### 4.6 质量门

- 明细合计与角色/阶段/总人天完全一致。
- 单位、舍入规则和公式版本明确。
- 所有高不确定项附理由和受影响范围。
- 低、基准、高三档关系单调且假设可解释。

## 5. DEL-PLAN 实施计划

### 5.1 目标

从工作包依赖、资源和里程碑生成可执行计划，禁止用总人天直接除以团队人数得到周期。

### 5.2 核心对象

| 对象 | 必要字段 |
|---|---|
| Phase | 编号、目标、起止条件、里程碑 |
| WorkPackage | 编号、范围、功能、角色、人天、持续时间、依赖、交付物、验收 |
| Milestone | 日期/相对周、完成条件、责任角色 |
| ResourcePlan | 角色、人数、可用率、并行限制 |
| Risk | 可能性、影响、触发信号、缓解与应对 |

### 5.3 计划规则

- 工作包来自功能、部署、迁移、测试、培训和文档等项目对象。
- 依赖图先于日期计算。
- 资源冲突、外部依赖和评审等待时间必须进入计划。
- 输出低、基准和高三档周期，并记录共同假设。

### 5.4 展示与输出

- 在线：时间轴、工作包表、里程碑、依赖和风险。
- XLSX：阶段、工作包、资源、里程碑、风险和验收工作表。
- DOCX/PDF：实施计划报告。

### 5.5 修改和影响

- 修改功能或人天触发相关工作包持续时间重新计算。
- 修改目标日期触发资源和依赖冲突检查，不能静默压缩工作量。
- 删除里程碑需检查交付物和验收覆盖。

### 5.6 质量门

- 不存在循环依赖、无负责人工作包或无交付物阶段。
- 总人天与估算成果一致。
- 日期满足依赖和资源约束。
- 核心交付物均有验收条件。

## 6. DEL-QUOTE 项目报价

### 6.1 目标

由工作量、角色成本、外部费用、风险、税费、利润和商务调整形成可解释报价。它与平台未来如何向用户收费无关。

### 6.2 核心对象

| 对象 | 必要字段 |
|---|---|
| QuoteLine | 类别、名称、数量、单位、单价、小计、可见范围、相关工作包 |
| ExternalCost | 第三方服务、许可、云资源、差旅等 |
| QuoteScenario | 竞争型/标准型/保守型、折扣、风险、利润、税费、总额 |
| CommercialTerm | 有效期、付款节点（项目报价内容）、变更规则、不包含内容 |

### 6.3 确定性规则

- 金额、税费、折扣、利润和总额全部由程序计算。
- 客户包不包含内部角色成本、利润率和内部假设。
- 币种、含税/未税和舍入规则必须显式。

### 6.4 展示与输出

- 在线：三档报价、明细、假设、包含/不包含和有效期。
- XLSX：报价明细、外部费用、策略、内部成本和客户版工作表。
- DOCX/PDF：正式报价建议书。

### 6.5 修改和影响

- 修改角色单价、税率、折扣只触发程序重新计算。
- 修改范围或工作量通过上游估算变更传递。
- 内部参数锁定后，客户包重新导出不能泄漏内部数据。

### 6.6 质量门

- 明细、分组、小计、税费和总额一致。
- 客户可见范围自动检查通过。
- 报价范围与方案、计划及需求范围一致。

## 7. DEL-SOLUTION 整体解决方案

### 7.1 目标

形成可用于客户沟通、内部立项和实施准备的长文档；内容必须引用正式项目模型，不以一次超长提示直接生成整篇。

### 7.2 默认章节

1. 执行摘要。
2. 项目背景与现状。
3. 客户、用户、目标和价值。
4. 建设范围与边界。
5. 需求与业务场景。
6. 总体业务、应用、数据和技术架构。
7. 功能与系统设计。
8. 接口、数据、部署、安全与迁移。
9. AI Agent 设计（如适用）。
10. 实施路径、组织、计划和验收。
11. 工作量、报价策略或商务摘要（按可见范围）。
12. 风险、假设、不包含内容和后续建议。

### 7.3 章节对象

每章包含目标、必引对象、允许篇幅、不可改变事实、正文、摘要、术语、数字、来源、依赖章节、质量结果和内容哈希。

### 7.4 展示与输出

- 在线：连续阅读、目录导航、来源侧栏和章节级状态。
- DOCX：自动目录、标题层级、图表编号、页眉页脚、引用和假设附录。
- PDF：与 DOCX 内容版本一致的只读交付版。

### 7.5 修改和影响

- 结构化对象变更优先更新项目模型，再重生成受影响章节。
- 用户直接修改段落时记录为用户锁定内容；相关数据变化必须提示冲突。
- 执行摘要和结论在正文完成后重新生成。

### 7.6 质量门

- 章节完整、顺序正确、无明显重复和矛盾。
- 术语、范围、关键数字和假设跨章节一致。
- 每个关键事实可追溯或明确标记为假设。
- DOCX/PDF 渲染无溢出、重叠、孤立标题和严重分页问题。

## 8. DEL-SLIDE 汇报演示

### 8.1 目标

形成 12—15 页左右的可编辑汇报材料，叙事来自同一项目模型和解决方案，而不是把长文档逐段压缩。

### 8.2 Deck 与 Slide 对象

| 对象 | 必要字段 |
|---|---|
| Deck | 受众、目的、叙事弧、模板、内容版本、渲染版本 |
| Slide | 编号、页面目的、标题、核心结论、内容块、图形意图、引用对象、演讲备注 |
| VisualBlock | 类型、数据、标签、布局约束、来源、可替换规则 |

### 8.3 默认叙事

1. 封面。
2. 背景与机会。
3. 当前问题。
4. 建设目标与范围。
5. 目标用户/场景。
6. 总体方案。
7. 架构。
8. 核心功能。
9. 数据/接口/安全或 Agent 能力。
10. 实施路径。
11. 工作量/周期。
12. 报价/价值。
13. 风险与假设。
14. 下一步。

页面数量根据内容和模板调整，不机械填满。

### 8.4 展示与输出

- 在线：缩略图列表、单页预览、页面目的、引用和备注。
- PPTX：原生可编辑文字、表格和基础图形，使用企业母版。
- PDF：逐页视觉一致的分享版本。

### 8.5 修改和影响

- 修改叙事或页面目的属于内容变更。
- 更换模板、Logo、颜色或版式属于渲染变更。
- 关键数字和结论来自引用对象，不允许模型在 PPT 中重新计算。

### 8.6 质量门

- 每页只有一个主要目的和清晰核心结论。
- 无超出安全区、文字截断、重叠、不可读字号或模板占位文本。
- PPTX 与 PDF 页面数量和关键内容一致。
- 所有关键数字和图表数据与项目模型一致。

### 8.7 主流程完成后的视觉优先复原

PPT 视觉质量专项采用“结构化内容锁定 → 生成视觉参考图 → 复原为语义 HTML → 映射为原生可编辑 PPTX → 回渲染比对”的链路，详细规则见 `12-ppt-visual-first-rendering.md`。

- 图片只作为视觉参考，不作为正文、数字、表格或引用的识别来源；禁止依靠 OCR 从生成图反向恢复交付内容。
- `Slide` 和 `VisualBlock` 是内容唯一事实源，各阶段必须保留稳定的内容标识并执行无损核对。
- 文字、基础图形、表格和可表达的图表必须恢复为 PPT 原生对象；复杂装饰插图可以作为独立图片层。
- 全套页面使用同一设计令牌、母版、网格和版式族，不允许逐页生成造成字体、配色和间距漂移。
- 该专项排在完整主流程 M8 验收之后，不改变当前阶段的 PPT 生成和交付链路。

## 9. 成果依赖图

```text
来源材料 / 用户确认
        ↓
正式项目模型
        ↓
需求分析 ─→ 功能清单 ─→ 工作量估算 ─→ 实施计划
                  │              │             │
                  └──────────────┴─────→ 项目报价
        └──────────────────────────────→ 整体解决方案
                                          ↓
                                      汇报演示
```

允许并行：需求稳定的业务域可以先进入功能；已稳定的功能组可以先估算。发布前必须运行全局一致性检查。

## 10. 成果包规则

| 包 | 默认包含 | 默认排除 |
|---|---|---|
| 客户交付包 | 客户可见需求、功能、方案、报价、计划、PPT 和 PDF | 内部成本、利润、详细来源、原始材料、内部备注 |
| 内部评审包 | 完整七类成果、估算依据、来源、假设和版本说明 | 原始材料默认不打包，除非用户选择 |
| 完整归档包 | 内部包、原始材料、模板、历史版本、修改记录和 manifest | 无；必须由用户主动选择 |

成果包使用同一内容版本。生成包时只执行权限过滤、文件渲染/复制、manifest 和 ZIP 组装，不调用模型重新写作。
