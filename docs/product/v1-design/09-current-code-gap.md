# 09 现有官网代码差距与迁移边界

## 1. 结论

现有官网/CMS 已被保留，独立产品域已经加入，主要 CTA 已接入产品入口。当前差距不再是“是否建立产品域”，而是把已跑通的本地单机链路收口为可验证、可迁移、可并发扩展的外部灰度版本。详细代码事实见 `13-current-implementation-status.md`。

## 2. 当前直接冲突

| 位置 | 当前行为 | 与 V1 的冲突 | 处理方式 |
|---|---|---|---|
| `app/components/Header.tsx` | 主 CTA 已指向 `/product/start` | 无直接冲突 | 保留“我的成果”与商务联系作为次要入口 |
| `app/components/HeroSection.tsx` | 默认主要 CTA 已指向需求画布 | 无直接冲突 | CMS 中的旧 Hero 配置应在下次内容发布时同步更新 |
| `app/components/ContactCTA.tsx` | 主入口改为“开始生成方案”；预约表单仅用于商务联系 | 不再作为产品前置步骤 | 保持预约域与产品项目状态机隔离 |
| `app/api/content/reservations/route.ts` | 写入 pending 预约，后台人工更新状态 | 与无人值守交付冲突 | 预约域保留商务用途，不进入产品状态机 |
| `app/cta/page.tsx` | 已改为直接开始形成项目成果 | 无直接冲突 | 保留商务联系表单作为企业采购/部署协助路径 |
| `app/components/DemoShowcase.tsx` | 文案包含“范围、价格与承诺由项目人员确认” | 正式运行不依赖人工处理 | 改为系统明确展示来源、假设和方向选择；用户确认仅限关键方向 |

## 3. 身份差距

### 当前

- `lib/auth.ts` 为管理员 JWT，payload 是数字 `userId` 和 `username`。
- 存在默认 JWT Secret，适合本地 CMS 演示，不适合产品用户生产认证。
- `lib/middleware.ts` 从 Authorization Header 读取 Bearer Token。
- 已增加独立产品用户名密码注册/登录和 HttpOnly Session、登录前草稿绑定，以及账号注销与异步清理接口；未来多方式登录仍待接入。

### 目标

- 管理员认证保持独立，不增加“管理员/产品用户共用 Token”的角色分支。
- 新建产品用户、登录挑战和服务端 Session。
- 产品浏览器交互使用安全 Cookie；下载另用短期签名地址。
- 登录后把 `draft_id` 原子绑定到产品用户，再创建内部项目和上传批次。
- 所有项目 API 从 Session 取得 user_id，不信任客户端 user_id。

## 4. 数据库差距

### 当前

- `lib/db.ts` 继续为官网/CMS 使用 `data/cms.db`；`lib/product/db.ts` 为产品域使用独立 `data/product.db`。
- 产品库已经包含身份、方案、材料、来源块、正式章节、项目模型、成果版本、删除、运行监控、配置发布和验收活动等表。
- Web 与长驻 Worker 共享 SQLite/WAL 契约，已实现租约、重试和幂等基础能力；当前仍是单机适配形态。

### 目标

- CMS 可以暂时继续使用 SQLite，避免无必要迁移影响官网。
- 产品域使用 PostgreSQL 和独立连接模块。
- Drizzle Schema 按产品领域拆分，不把 JSON 正文塞入单一 delivery_content 表。
- Web 与 Worker 使用同一数据库契约，但分开连接池和权限。
- 数据库任务表承担 V1 队列、租约、幂等和重试。

## 5. 文件差距

### 当前

- `/api/upload` 继续只承担 CMS 图片上传；产品上传位于 `/api/product/solutions/:solutionId/uploads/:fileId`，两者不共用状态机。
- 产品材料、企业模板、品牌素材和成果写入 `PRODUCT_PRIVATE_STORAGE_PATH`，不进入 `public/`。
- 产品上传已经校验声明类型、真实格式、SHA-256、资源风险和用户/方案/文件归属，并使用短期令牌下载成果。
- 当前私有存储适配器仍是本地目录，尚未迁移到对象存储和恶意文件扫描服务。

### 目标

- 产品上传使用独立 `/api/product/uploads/*`，进入私有对象存储。
- 内容材料、企业模板和品牌素材拥有不同 category。
- 服务端验证 magic bytes、扩展名、检测 MIME、大小和资源风险。
- 上传完成后创建 source revision 和解析任务。
- 下载通过项目鉴权后生成短期签名地址。
- 原始文件名加密保存，storage key 使用不可预测 ID。

## 6. 异步处理差距

### 当前

- 已有 `scripts/product-worker.mjs` 长驻 Runner、统一流水线 tick、阶段独立 tick、数据库租约、幂等、退避重试、超时回收和章节续跑。
- Runner 已分别维护生成、删除、运行快照和私有存储维护循环，并通过心跳、外部健康探针和 systemd 进行单机恢复。
- 当前未完成的是多主机队列、水平扩缩容和生产容量验收，而不是 Worker 功能从零实现。

### 目标

- Next.js API 只创建任务、查询状态和处理短事务。
- Node.js Worker 执行验证、解析、OCR、模型、计算、渲染、检查、打包和删除。
- 每个任务有输入哈希和幂等 Key；Worker 使用租约避免永久 running。
- 长文档细分到语义小节；Office/PDF 细分到文件/页面/工作表。

## 7. 页面与导航迁移

### 阶段 A：技术验证期

- 不改变现有首页主流程。
- 使用仅研发可见的最小内部入口运行基准项目。
- 避免把未达到质量门的原型暴露为“产品已上线”。

### 阶段 B：最小链路可用

- 增加真实需求画布和产品登录。
- Header 增加“开始生成方案”，但可暂时保留商务联系。
- 旧预约数据与产品项目完全分开。

### 阶段 C：七类成果与无人值守通过

- 官网主要 CTA 全部切换到产品入口。
- “申请项目分析”从主要流程移除或改为次要商务联系。
- 更新 Demo 文案，删除人工确认交付的暗示。
- 增加“我的方案”和产品用户状态入口。

## 8. 外部灰度前必须解决的决策

这些决策不能凭文案或 UI 临时决定，但可以通过技术验证得出：

1. PostgreSQL 和私有对象存储的部署环境。
2. 密码找回方式、共享登录限流和未来多方式身份供应商。
3. 多格式解析与 Office/PDF 渲染工具链的生产许可、资源隔离和容量配置。
4. Worker 多机队列、部署、监控和自动扩缩方式。
5. 模型供应商数据保留与区域配置。
6. 字体许可和企业模板字体替换策略。
7. 暂定留存期和单项目上传安全阈值。

## 9. 不应做的快捷改造

- 不把 ContactCTA 增加文件上传后直接称为产品入口。
- 不给现有管理员 JWT 增加 product role 后共用认证。
- 不把用户材料写入 `public/uploads`。
- 不在 Next.js 请求内同步等待长文档或 Office 生成。
- 不让七个页面分别调用模型生成七份互不关联的自由文本。
- 不在支付设计前将免费/正式阶段硬编码为订单状态。
